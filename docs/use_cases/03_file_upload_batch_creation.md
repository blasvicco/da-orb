# UC-3: File upload → batch creation from file content

Uploaded file content (CSV/PDF/etc.) becomes multiple create requests. Same batch-execution path as UC-2/UC-5 from extraction onward — the only difference is that `Agent: Extract Batch Records` reads records from file content instead of message text.

## Scenario

```
User uploads a CSV and a PDF file that contain purchase request data, and says:
"Usa el contenido de estos documentos para crear las solicitudes de compra."
```

This is mechanically the **same batch-execution path as UC-5** (multiple instances of the same process) from `context-update.json`'s extraction step onward — the only difference is where `Agent: Extract Batch Records` gets the record data from (file content here, inline message text there). It's documented separately because the file-extraction pipeline that runs first is a substantial, distinct piece of machinery.

## Preconditions

The two files must already exist in the session's bucket (uploaded via the separate upload endpoint before this message is sent) — `bucket_file_ids: [101, 102]` are their ids, `101` = CSV, `102` = PDF.

## Turn-by-turn trace

### File extraction (runs first, unconditionally, before intent classification)

**`context-enrichment.json` → `Execute Workflow: File Extraction Core` → `file-extraction-core.json`:**
1. `Has Files?`: `bucket_file_ids.length > 0` → true.
2. `Split Files`: `[101, 102]` → 2 items, `{bucket_file_id, org_slug, access_token}` each.
3. `Execute Workflow: File Content Extractor` receives both items in **one** call — despite the "runs once per item" framing this used to have, n8n does not spawn a separate execution per item here; it runs every downstream node once per item *within a single sub-workflow execution* → `file-content-extractor.json`:
   - `Check Cache` (`GET /api/v1/bucket/extraction/?file_id=...`) → `Has Cached Content?`: the true branch (cache hit) and the false branch (`Execute Workflow: File Extraction Item` → `file-extraction-item.json`, below) both feed into `Merge Cache Outcomes` (an n8n `Merge` node, append mode) before `Ensure Bucket File ID` fills in `bucket_file_id` **only when it's not already correctly present** — required so a batch mixing a cached and an uncached file doesn't lose one of them (see "Notable gaps" for the real incident this fixed, and why the re-tagging logic itself needed a second fix, including the rename from this node's original name `Attach Bucket File ID` to make its different, more defensive behavior obvious at a glance next to `file-extraction-item.json`'s node of that same original name).
     - `file-extraction-item.json` (cache-miss path): `Get Presigned URL` (`GET /api/v1/bucket/download/?file_id=...`) → `Download File` (binary) → `Route by Mime Type` on `$binary.data.mimeType` fans out into one branch per supported type (`text/csv` → `Extract: CSV`, n8n's built-in Extract-From-File, one item per row; `application/pdf` → `Extract: PDF`, one item; similarly for XLS/XLSX/ODS/HTML/JSON/RTF/TEXT) plus an `Handler: Unsupported Format` short-circuit for anything else. Every supported-type branch feeds into `Merge Extraction Branches` (a `Merge` node, append mode) before `Normalize Extraction Result` — required because a batch mixing file types (a CSV + a PDF) sends each file down a *different* branch, and without an explicit merge only one branch's items would survive (see "Notable gaps"). `Normalize Extraction Result` then groups the combined stream back into one result **per originating file**, recovered via `pairedItem`/`itemMatching()` lineage back to the trigger node (`bucket_file_id` itself is long gone from `$json` by this point — `Get Presigned URL`'s own response overwrote it several nodes earlier), and stringifies each file's own rows into its own `extracted_content`. That flows to `Persist Extraction` (`PATCH /api/v1/bucket/extraction/`, caches it for next time) or, for the unsupported-format branch, `Handler: Unsupported Format` (never persists) — both paths merge again at `Merge Extraction Outcomes` before a final `Attach Bucket File ID` re-tags each item with its correct `bucket_file_id` (neither path carries it as a literal field yet) and returns.
4. `Merge File Extractions` matches each result back to its `bucket_file_id` by that explicit field, not by array position (position broke whenever branches reordered items relative to the original `bucket_file_ids` order — see "Notable gaps"):
   ```json
   "extracted_files": [
     { "bucket_file_id": 101, "extracted_content": "[{\"ItemCode\":\"A001\",\"Quantity\":\"10\", ...}, {...}]", "error": null },
     { "bucket_file_id": 102, "extracted_content": "Purchase Request — Supplier: V10000\nRequired Date: 2026-09-15\n...", "error": null }
   ]
   ```
   No size cap is applied here — the full content of both files rides along uncapped from this point on (a 2000-char preview cap only exists in `general-inquiry.json`'s context block, not in the batch path — see the README's known-gaps list).

### Turn 1 — the message + files

**`agent-intent-finder.json`:**
- `Agent: Find` receives the message **and** `extracted_files` in its `INPUT JSON`. Per its own rule ("if the request references attached files, use whatever file content already appears in the INPUT JSON to identify the process(es)"), it reads both files' content, recognizes it's all Purchase Request data → **one distinct process**, not two (multiple *records* of the same process still collapse to one `processes` entry): `{"status": "new_intent", "new_intent_status": "batch", "processes": [{"path": "purchase/purch_request/purch_request.json", "process_name": "Purchase Request"}]}`. The `batch` vs `match` call is driven by **the user's own wording**, not by how many records the file content actually turns out to contain — that real count isn't reliably knowable at this step (extraction/structuring happens later) and isn't Agent: Find's job to pre-compute. An open-ended file reference like this scenario's ("con el contenido de estos archivos", no limiting phrase, plural "solicitudes") defaults to `batch` — the user is asking for however many records the files contain, even if that turns out to be just one once parsed. Only an explicit single-record phrasing (e.g. "usa el primer registro de este archivo para crear una sola solicitud") resolves to `match` instead — in which case `sap-process-form-filling.json`'s `Prompt: Form` node also reads `extracted_files` and injects an `ATTACHED FILE CONTENT` block into its prompt, so the single-process form-fill agent can pull field values straight from the file too (see "Notable gaps" below).
- `Compute Route Key` → `route_key = 'batch_processing'`.

**`intent-manager.json`:** no park (`active_node_id` is `null`).

**`context-update.json`:** `Needs Resolution?` true → resolves the **one** Purchase Request schema (same 3-tier GitHub cascade as UC-1) → since `route_key === 'batch_processing'`, `Needs Batch Extraction?` also runs **`Agent: Extract Batch Records`** for this process in the same loop iteration (see UC-2's architecture note). Its prompt includes:
  ```
  ATTACHED FILE CONTENT:
  File 101:
  [{"ItemCode":"A001","Quantity":"10", ...}, {...}]

  File 102:
  Purchase Request — Supplier: V10000
  Required Date: 2026-09-15
  ...
  ```
  Per its systemMessage, "identify every separate record the user wants to create for this process" — parses both files' content (CSV rows as discrete records, PDF text as prose describing one or more records) and returns `{"records": [{...form_state}, ...]}`, one entry per record it identifies (could be many, from the CSV alone) — field-id-keyed `form_state`, **not** a submitted payload; it never calls any tool, never touches SAP itself. `Build Intents`: `intents: [{path, process_definition, error: null, items: [<extracted record 1>, <extracted record 2>, ...]}]` — exactly one intent entry (one distinct process type), with as many `items` as records were found across both files. `Which Flow?` false (`batch_processing` ≠ `sap_form_filling`) → no node registration *here* — `batch-processing.json` registers its own real `intention_nodes` entries later, once per record actually submitted, after the fact.

**`Router`** → `Batch Processing`.

**`batch-processing.json`:** thin loop only — no agent of any kind runs here. `Fan Out Intents` reads this intent's already-extracted `items` and flattens them straight into N work items in one pass — one per record found across both files, each stamped with `_record_index`/`_record_total` (1-based position among every *real* record in the whole turn, across every intent — `_skip_execution` markers are excluded from both the count and the numbering, see "Notable gaps" below) — each flows through `Prepare SAP Inquiry Call` → `Execute Workflow: SAP Inquiry Execution` (`mode: "each"`, the real `sap-inquiry-execution.json`, unmodified structurally — its own `Build SAP Payload` does the field-id → sap_field mapping and calls `sap_entity_create` once per record) → `Record Execution Result` → `Group Results By Intent` (groups all N record results back under the one Purchase Request intent) → `Compose Batch Summary`: `"**Ejecución por lotes completada**\n- Purchase Request: 4 creadas, 1 fallidas"` (illustrative — actual counts depend on what the CSV/PDF contained) → the same registration pass every batch path shares (`Check Registration Needed`, fanning out directly into per-registration items, → one `Execute Workflow: Register Intention Node` call registers every record from the whole turn) → `Resolve Final State` (auto-resumes `active_node_id` to whatever this upload interrupted, if still open — see UC-2/UC-4) → `Execute Workflow: Response` → Django callback.

**Per-record progress:** each record's own `mode: "each"` sub-execution of `sap-inquiry-execution.json` independently POSTs its own `type: "status"` ping to `n8n_callback` — sequential `mode: "each"` runs one record's whole sub-execution to completion before starting the next, so these pings arrive genuinely inline, not all at once at the end. This reuses the sub-workflow's existing `Status Text: Submitting` → `Status: Submitting` nodes (the same ones that fire on every non-batch SAP call): `Status Text: Submitting` checks for `_record_index`/`_record_total` on its input and, when present, builds `"Procesando {N} de {M} solicitudes..."` instead of the generic `"Enviando a SAP"` text. See UC-README's callback/status-message mechanism (`type: "status"`, ephemeral, broadcast-only) for why this is safe to fire N times per turn.

**Final state:** `intention_nodes` gains one new entry **per record actually submitted** across both files (CSV rows + whatever the PDF described), each carrying that record's own submitted `form_state` and `status: "completed"`/`"failed"` — not one shared entry for the whole batch item. `active_node_id` resumes to whatever this upload interrupted, if it's still open (reactivated to `active`), or `null` if there was nothing to return to — see UC-4. A failed row is individually clickable in the sidebar and correctable per UC-6/UC-11, same as any other failed process. Delivered message is still just the summary line.

## Notable gaps (see also README "Known gaps")

- **Extraction is still one LLM call per intent, not per record.** `Agent: Extract Batch Records` runs once per distinct *process type* found across the attached files, not once per individual record — this matches `docs/plans/upload_and_file_bucket.md`'s design (a single agent reasoning over every attached file's full content in one pass, chosen specifically to catch data split across files), so there's no per-record "extracting record N..." granularity during that phase. **Per-record progress during execution IS reported**: each record's own `sap_entity_create`/`sap_entity_get` call broadcasts `"Procesando N de M solicitudes..."` via `n8n_callback` (`type: "status"`) as it happens — see the turn-by-turn trace above.
- **A failed extraction (unsupported file type, e.g. a `.docx` or an image) yields `extracted_content: null, error: "UNSUPPORTED_MIME_TYPE"` for that file** — `Agent: Extract Batch Records`'s prompt shows `File 102:\n(no content)` for it and simply has less to work with; there's no explicit "some of your files couldn't be read" surfaced to the user beyond whatever the agent itself chooses to say.
- **A failed presigned-URL download throws** rather than degrading into a per-file `error` (see README) — this would fail the whole turn's file-extraction sub-execution, not just skip that one file.
- **[Fixed 2026-08-16, live] Four compounding bugs meant file-sourced record creation silently lost data** — sometimes re-asking for values already present in the file, sometimes dropping an entire file's records outright. Found and fixed by tracing four consecutive real production turns (sessions 325–328) end-to-end against live n8n execution logs, not just static code reading:
  1. **Misclassification (`agent-intent-finder.json`, `Agent: Find`).** The old prompt only forced `batch` when it judged the file content "should become multiple records." An open-ended file reference whose content happened to resolve to exactly one usable record (one file failed extraction, the other held a single complete Purchase Request) fell through to `match` instead — even though the message itself never limited the request to one record. Fixed so `batch` vs `match` is driven purely by the user's own wording (an open-ended file reference → always `batch`; an explicit single-record phrasing like "usa el primer registro de este archivo para crear una sola solicitud" → `match`), never by pre-counting records, which isn't reliably knowable at classification time.
  2. **`match` path blind to files (`sap-process-form-filling.json`, `Prompt: Form`).** This node never read `extracted_files` at all — verified directly against a live execution that the actual `chatInput` sent to the LLM had zero occurrences of "extracted" or "file" anywhere in it, despite the file's content sitting unused in the node's own input. This meant even a *legitimately* single-record file upload (explicit phrasing, correctly classified `match`) would still hit the same symptom. Fixed by injecting an `ATTACHED FILE CONTENT` block into the prompt when `extracted_files` is present, mirroring `Agent: Extract Batch Records`'s existing pattern.
  3. **Unmerged parallel branches silently drop whole files (`file-extraction-item.json`, `file-content-extractor.json`).** `Route by Mime Type`'s per-type branches, and separately the cache-hit/cache-miss branches, both fanned into their next node with no `Merge` node joining them first. When a batch mixed file types (a PDF + a CSV), each file went down a *different*, disconnected branch — and n8n's `Execute Workflow` node, when a sub-workflow's return point fires as multiple separate branch-runs instead of one unified run, only hands the *last* branch's items back to the caller. Verified directly: the CSV's 3 rows were correctly extracted and even persisted to cache, but never survived the trip back across the sub-workflow boundary — `extracted_files` showed that file as `extracted_content: null` despite extraction having actually succeeded. Fixed by adding `Merge Extraction Branches` and `Merge Extraction Outcomes` (in `file-extraction-item.json`) and `Merge Cache Outcomes` (in `file-content-extractor.json`) to join every branch into one stream before returning.
  4. **Fragile array-position matching, and one unreliable `itemMatching()` call across a sub-workflow boundary.** The outer `Merge File Extractions` originally zipped `bucket_file_ids` to results *by array index* — which breaks the moment branches reorder items, which they do once #3 above is fixed and multiple mime types are involved in the same batch. Fixed by tagging every result with its real `bucket_file_id`, recovered via n8n's `pairedItem`/`itemMatching()` lineage, and matching by that field instead of position. That lineage is reliable *within* a single workflow but **not** across an `Execute Workflow` (sub-workflow) call boundary — the first attempt at this used `itemMatching()` unconditionally in `file-content-extractor.json`'s bucket-file-id-tagging node (then also named `Attach Bucket File ID`, same as `file-extraction-item.json`'s node — since renamed to `Ensure Bucket File ID`, both to make its different, more defensive behavior obvious at a glance and to remove a same-name collision across files that Tier 1's node lookup, `workflow/tests/engine/workflow_loader.js`, silently assumes can't happen), which sits immediately after exactly such a boundary. It mis-resolved and re-tagged every item with the same wrong id, silently clobbering the correct `bucket_file_id` that had already ridden through intact from the child workflow (confirmed by diffing the item's field value immediately before vs. immediately after that node). Fixed by preferring the value already present on the item and only falling back to `itemMatching()` on the cache-hit path, which never crosses a sub-workflow boundary.
  5. **`Agent: Extract Batch Records` merged multiple CSV rows into one record's `items` array instead of treating each row as its own separate record**, even though its own systemMessage already said "a CSV row" counts as a record — confirmed against a real production execution (session 329) where a 3-row CSV (three different requesters, sharing the same Supplier/RequriedDate) produced only 2 total Purchase Requests instead of 4, because the LLM inferred "same header fields → same request" despite the explicit instruction. Fixed by adding a hard, mechanical rule to the prompt: a CSV row is *always* its own record, and shared header-level values across rows never imply they belong to the same request.

  All five fixes are live in the running n8n instance (pushed directly via the n8n public API `PUT /api/v1/workflows/{id}`), not just committed to this repo's workflow JSON. Every deterministic (non-LLM) piece of this — `Merge File Extractions`, `Normalize Extraction Result`, `Attach Bucket File ID`, `Ensure Bucket File ID`, and `Build Intents`' multi-record passthrough — now has Tier 1 unit coverage (`workflow/tests/cases/unit/`), including regression cases for the exact out-of-order/missing-result/cross-boundary-overwrite shapes that broke in production; `Merge File Extractions`' matching-by-id behavior additionally has Tier 2 coverage (`path_file_extraction_core.json`). `Agent: Extract Batch Records`'s CSV-row-grouping fix is prompt-only and has no automated test — LLM judgment isn't something a pinned test can verify — so it depends on live/manual re-verification.

## Spec test outline

Closest existing models: `workflow/tests/integration/batch_execution_test.py`/`batch_confirmation_test.py` exist but target a **stale, pre-v14 workflow ID** (`ORBOT_WORKFLOW_ID = 'A4tWYpCiZA0EQgCE'`, "Orbot v6"/"Orbot v8") and reference dead fields (`awaiting_batch_confirmation`, `pending_batch_items`) — do not extend these; they need a full rewrite against the current spine (`gl7Ax8b77WhVUTmw`) before they're trustworthy again, or should be retired in favor of new tests modeled on this doc.

- **Tier 1 — [Done 2026-08-16]**: `Split Files` already had coverage; `Merge File Extractions`, `Normalize Extraction Result`, `Attach Bucket File ID` (`file-extraction-item.json`), and `Ensure Bucket File ID` (`file-content-extractor.json`) now do too. `merge_file_extractions.json` covers a missing result (`MISSING_EXTRACTION_RESULT`) and out-of-order results matched correctly by `bucket_file_id` rather than array position. `normalize-extraction-result.json` covers rows from two different files interleaved in one combined stream grouping back into two separate results. `ensure-bucket-file-id.json` covers the actual regression: an item that already carries a correct `bucket_file_id` must survive untouched even when `itemMatching()` would resolve to something else. `build-intents.json` gained a case with a populated multi-record `items` array (4 records) passing through unchanged, validating the shape handed to `batch-processing.json`. This required extending the test harness itself (`workflow/tests/engine/n8n_context.js`) to support `.itemMatching()`, which none of these nodes' code could previously be tested against at all.
- **Tier 2 — [Done 2026-08-16]**: `path_file_extraction_core.json`'s existing multi-file case was stale (asserted a shape the harness's own `runOnceForEachItem` pin semantics couldn't actually produce) — fixed and strengthened into a real regression case: a pin can only return one literal (`bucket_file_id: 101`, duplicated per item), so 101 must resolve correctly while 102 correctly surfaces `MISSING_EXTRACTION_RESULT` — proving the matching genuinely discriminates by id rather than coincidentally passing. Still open: no Tier 2 suite exercises `file-extraction-item.json` directly (a mixed-mime-type CSV+PDF case through the real `Extract: CSV`/`Extract: PDF` nodes) — infeasible with this framework's pin mechanism as-is, since pins only inject `json`, never `binary`, and `Extract: CSV`/`Extract: PDF` read from `$binary`. Would need either real bucket-file fixtures (see the Live E2E note below) or a framework extension to pin binary data.
- **Tier 2 — still open**: extend `path_context_update.json` with a case whose input carries no inline message data but the shared context carries `extracted_files` — pin `Agent: Extract Batch Records` to return N records, assert `items` on the returned intent carries all N. (`build-intents.json`'s new Tier 1 case covers the downstream passthrough of an already-multi-record intent; this would cover the resolution step feeding it, still untested.)
- **Not testable via pins**: `Agent: Extract Batch Records`'s CSV-row-vs-line-item grouping (session 329's actual bug — it merged 3 CSV rows into one record's `items` array despite its own prompt saying "a CSV row" is a record) is real LLM judgment, not deterministic code — a pinned test can assert the *downstream* plumbing handles N records correctly (now covered, see above) but can't verify the agent itself reliably produces the right N for arbitrary CSV content. Only a live E2E run with a real OpenAI call can catch a regression here.
- **Live E2E**: upload a real small CSV (2-3 rows) via the bucket endpoint, send the trigger message, poll for delivery, then assert (a) the summary message's counts match the CSV row count, (b) `intention_nodes` gained one new entry per row, each `form_state` matching that row's own submitted payload, (c) inspecting the real SAP MCP tool calls (via `client.get_node_output(execution, 'Agent: Execute')`, inside the nested `sap-inquiry-execution.json` child execution, run once per record) shows one `sap_entity_create` call per CSV row. Model on `workflow/tests/integration/phase4a_intention_nodes_object_shape_test.py`'s structure but note this one needs real bucket-file setup first (check `app/backend/drf_api/resources/bucket/` for the upload endpoint to script against).
